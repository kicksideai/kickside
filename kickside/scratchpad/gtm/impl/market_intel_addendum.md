DESIGN ROUND 2 INPUT — Market Intelligence component (owner, 2026-07-10 late):
A component for continuous market research: DIGESTION (understand a market/domain: players, segments, dynamics), SCANNING (periodic sweeps for companies/signals), DEEP SCANNING (drill into a found company), then SOURCING (emit candidate rows → import session → the conveyor). Runs in the BACKGROUND on a CADENCE — one of the automations (periodic trigger vocabulary exists: kickside.automation:periodic_trigger_point). John needs the WHOLE PICTURE — the component owns an evolving market view, not one-shot results.
Assembled from AGENTS (research/digestion/deep-scan are agent work over research+webscout+phantombuster tools) + WORKFLOWS (orchestration through hooks/archetypes per the round-1 spec).
HARD REQUIREMENTS:
1. DEDUP across cadence runs: the same company/lead must never be re-sourced or re-proposed. Map onto existing vocabulary: person dedup = alias reservations (exists); COMPANY/market-entity dedup needs a keyed identity (domain-first) + a seen-registry on the component (sourced/parked/rejected states, resurfaceable like candidate parking — a rejected company may resurface only on NEW evidence, same skip semantics as merge review).
2. SEMANTIC HISTORY: the component accumulates searchable memory — market digests over time, scan findings, why companies were rejected/parked, what changed — so scans are INCREMENTAL (agents query history before proposing) and John can ask "what do we know about this market". Natural mapping: ONE KB per market component (document/graph kinds exist; note owner's task #32 concern is per-CONTACT KB explosion — per-MARKET is coarse-grained and fine) + a structured seen-registry read-model (projection) for the dedup facts; the KB holds prose/findings, the projection holds keyed state — do not conflate them.
3. The whole picture surface: the market component's detail view = digest summary + funnel (companies seen → sourced → became leads → became deals) + history timeline.
Design questions for round 2: component kind shape (one market_watch kind, instance per market/ICP lane?), how agents are bound (traits on a per-component agent? hooks calling agent-backed workflows?), cadence config (per-stage cadences: scan daily, digest weekly?), how deep-scan is triggered (auto for high-signal finds vs operator-requested), and the seen-registry contract so ALL discovery sources (prospecting requests from round-1 spec B included) share ONE dedup layer.
4. THREAD-MANAGED (owner): the market component manages its state in its OWN THREAD per the canonical component model — digests, scan results, source/park/reject decisions, deep-scan findings are THREAD EVENTS; the seen-registry, funnel, and timeline are PROJECTIONS over that thread (component-owned read-model law; the CRM CQRS topology is the reference). The KB holds the semantic/prose layer; the thread holds the factual event history; projections hold the queryable state.
5. COMPETITOR RESEARCH feeds the design: how Ocean.io/Clay/Apollo/Common Room/Koala/ZoomInfo/Bombora-class products do continuous market+lead intelligence (market mapping, signal feeds, intent data, dedup/suppression, incremental discovery, "what do we know" surfaces) — luna sweep in flight, findings to be consumed by round 2.

MODEL ON THE CRM (owner): argue market-intel entities living ON the CRM substrate rather than a component-local store — market/segment as config-declared object types, scanned companies as CRM records in a pre-lead class (the prospect_candidate quarantine precedent), the seen-registry as CRM-record state + projections. Substrate law favors this ("never a parallel entity store"); round 2 must argue CRM-modeled vs component-local and pick, considering: schema noise in the CRM UI (default-hidden classes), volume (thousands of scanned companies), and the dedup layer being shared with person/company identity machinery.
7. CRM CONFIG IMPORT/EXPORT as another stream (owner): the CRM configuration authored in the admin panel (System > CRM schema manager — object types, attributes, policies) must be exportable/importable as a portable artifact — config-as-stream for environment promotion and whitelabel templates (gtm_pack requirement; constraints env-promotion). Round 2: where this lands (crm capability? part of the definitions/export vocabulary workflows already have for defs?), format (declaration-shaped YAML/JSON), and how an import merges with the reconcile rule (declaration wins for titles/order, user data preserved — the existing ensure/reconcile semantics extend).
8. THIN PROVIDERS, CONFIGURABLE CAPABILITIES (owner, on the calendar lane): do not hardcode provider-specific capabilities — Google is ONE binding of a generic capability, not its owner. The pattern: providers expose thin declared adapters (a calendar-read contract: "upcoming events"), and the CAPABILITY (pre-meeting timing, internal-domain filtering, attendee fan-out → brief) lives as a configurable workflow/playbook over that contract — swappable provider, replaceable logic (flow.points). Applies retroactively: the just-built google calendar poll source carries logic (windowing/lead-time/filtering) that belongs in a playbook over a thin events-pull; schedule that migration with the catalog/market-intel builds, not as churn now. Same rule for every future discovery capability: agent/workflow over declared provider tools, never provider-embedded logic.
