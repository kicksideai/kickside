# Workflows v2 — decision record (Fable)

Owner directives: re-architecture licensed; everything exportable/portable across environments; the GTM system must build on the corrected primitives (no half-refactor later).

## W1. Definition/binding split (rules the trigger fuzz)
A workflow DEFINITION is a pure function: typed input schema -> typed output schema, zero triggers inside. A TRIGGER BINDING is a separate small artifact: (event source | schedule | webhook | in-app button) -> (workflow ref + input mapping), owned by the automation layer. Consequences, all binding:
- No trigger nodes on the canvas, ever. The builder edits definitions only; the automation UI (and in-app embeds) edit bindings only.
- Nesting: a `Call workflow` node invokes a child DEFINITION (sync: await output; or async: run id + lifecycle events). Child's bindings are irrelevant to callers.
- Workflow-as-agent-tool: the tool schema IS the definition's input schema; same call path as nesting.
- Embeddable "add trigger here" web component: a generic binding-creator hosted by any app; its source is the host app's declared event; its target is a definition picked via the workflow picker (mirror the agent picker pattern).
- Lifecycle: run.started / run.finished / run.failed are uniform run events regardless of invoker; consumable as trigger sources themselves (workflow chains), by signals, and by dashboards.
- Portability: definitions export as portable artifacts (portable_key + refs per gtm decisions A6); bindings export separately with sources/connections as slots. Either side moves environments without the other.

Open for the design doc (after recon): migration path from current trigger install mechanism; whether run invocation gets a single `runs` contract other modules call (CRM, agents, playbook routing all converge on it); input-mapping language for bindings (same mechanism as edge transforms — one schema-connect primitive, asks C).

## W2. The universal triad: trigger point x runnable x mapping (owner-stated)
The entire automation/configuration surface reduces to three platform primitives; everything else is config:
1. TRIGGER POINTS — declared by DOMAIN modules, each with a context schema (what it provides). Kinds: domain events (record.updated, stage TRANSITION), in-UI record ACTIONS ("for this entry, this action: click here" — an action declared on an object type/view, context = record id + user + workspace), schedules, webhooks, run-lifecycle events. A domain module declaring a trigger point does not know or care what gets bound to it.
2. RUNNABLES — anything invocable with a typed input schema: workflow definitions (W1), agents, tools, sink/recipe dispatches (the existing automation dispatch seam). One invocation contract; the runnable kind is a detail.
3. MAPPING — schema-in -> schema-out, the single schema-connect primitive: deterministic transform, AI-generated-then-frozen transform, or LLM-in-the-middle at runtime. Same primitive serves edge transforms, binding input mappings, and workflow-as-tool argument mapping.
A BINDING = (trigger point, runnable, mapping) — pure config, portable, created from universal web components any app hosts: the action/trigger attacher ("add trigger here" / "add action here"), the runnable picker (workflow/agent/tool — mirror agent picker), and the mapping editor (schemas + AI propose + approve).
Canonical example: CRM record action "Run research" = binding(trigger point: person.record_action, runnable: research workflow definition, mapping: {record_id -> contact_id, requested_by -> user_id}). Stage-transition play = binding(opportunity.stage_transition, revival workflow, auto-proposed mapping). Zero code in either.
Also: notes/documents attach at record level as component references (rides CRM S6 per-record KB/doc attachment) — record-scoped context any bound runnable can read.
GTM consequence: CRM (and every domain module) ships trigger-point declarations + action surfaces as part of its constructor contract; the GTM "playbook routing" is just bindings over signal trigger points.

## W3. The triad REDUCES the existing vocabulary — it must not become another layer (owner directive)
The platform already carries multiple overlapping automation vocabularies: poller sync (source -> transform -> sink), automation recipes/dispatch, workflow trigger installs, scheduled actions, webhook installs — plus W2 adds record actions. The triad is the CONSOLIDATION of all of them, not an addition:
- Trigger points ABSORB source ports, domain events, schedules, webhooks, run-lifecycle events, UI actions. One declaration grammar with a context schema.
- Runnables ABSORB sink dispatch, recipes, workflow runs, agent/tool invocation. One invocation contract.
- Mapping ABSORBS sync transforms, edge transforms, binding input mappings.
- A poller sync recipe IS binding(source trigger point, sink runnable, mapping) with a poll schedule. The Gmail case — "read my inbox, classify each email, kick off a process" — is binding(gmail.message trigger point, classifier workflow/agent runnable, mapping), and the kicked-off process is that workflow calling the next definition. No special sync vocabulary remains visible to the operator.
- Acceptance criterion for the v2 design: the operator-facing vocabulary SHRINKS (count the artifact kinds an operator must understand before/after; after must be lower). Existing vocabularies migrate or become internal lowerings; none survives as a parallel operator-visible concept. Vocabulary count is a gate metric in the design review.

## W6. Rulings on the wfv2 attack (wfv2_attack.md — all accepted, key resolutions)
1. TWO INVOCATION MODES under one Call contract (resolves F1/F8/F10): default = SPAWNED child run (a real run with its own lifecycle events, durable AWAIT, A4 recovery, parent links child via run id + completion signal); INLINE fold-in is reserved for pure, fast, non-AWAIT transforms (mapping-grade functions) and carries no independent lifecycle by design. Call sites choose; the builder defaults to spawned for workflow-typed runnables. Per-child accounting/lifecycle exists only in spawned mode — the design stops pretending inline children have runs.
2. Domain business-node contribution is a W-A FIRST-CLASS contract (resolves F2/W5): node model gains input_schema; the node->definition and node->WC-config seams enter the artifact contracts; CRM ships `Resolve contact` as the reference domain node in GTM P0/P1. W5 litmus must pass on BOTH halves (trigger/binding AND node contribution).
3. Lifecycle events use the A10 canon-4 cross-runnable schema, not a workflows dialect (F3). Runnable descriptor/discovery is a declared catalog contract like sources/sinks (F4).
4. Migration: bindings carry the legacy trigger_id during dual-run so the dedup index bridges; no flag day (F5). Vocabulary gate passes only after sync reconcile parity is included (F6).
5. A3 dispatch-time identity/permission revalidation is confirmed ABSENT in code — becomes an explicit W-A work item (bindings run under component-owner/service identity, revalidated at dispatch; installer recorded as audit only). Binding authority must cover the runnable's transitive side effects via its declared scopes (F7).
6. No runtime document-recompile: frozen-command transforms preserve the immutable-version invariant (F9). The func node 100ms output-poll silent-complete is an ENGINE bug to fix at the engine, tracked with the fold-in work (F10).
7. Partial boundary nodes (owner directive 2026-07-09): a partial's contract is expressed IN THE GRAPH as explicit boundary nodes — Start (input schema), Finish (output schema), and Error (error schema; a first-class second exit, not an afterthought). A workflow with these boundary nodes declared IS a partial/composite; the interface derives from the boundary nodes, not a parallel metadata field. Error propagates to the caller as the failed branch of the Call node.
8. Pinned-boundary designer mode (owner directive): when editing a partial, the canvas PINS the Start/Finish/Error nodes — non-deletable, schema editable at the boundary; edges validate against the pinned shapes so composition is designed against the contract. When a partial is placed inside a larger workflow, the Call node renders the child's pinned shapes as its port schemas.
9. Runner contract (owner directive): one declared contract to run a workflow and get a durable descriptor back — mirror the userspace.dataflow:execution_identity pattern (contract entry + default contract.binding, consumed via requirement, never direct imports). Shape: run(workflow_ref/version, input, opts) -> descriptor {run_id, status}; completion/output/error observed via the A10 run lifecycle events (run.started/finished/failed) keyed by run_id. The Call-workflow node, recipes/automation pickers, and ANY embedding module all invoke through this single contract — same seam whether the caller is a workflow, an agent tool, or an app surface.

## W9. No triggered-workflow species (owner directive 2026-07-09, supersedes any in-canvas trigger grammar)
A workflow is a PURE, TYPED FUNCTION artifact: Start(input) -> Finish(output) | Error(error). Every published workflow is callable — the "partial" distinction dissolves (it named the transition, not a kind). Triggers exist ONLY in the automation layer: an automation = trigger point + workflow (runnable) + mapping, created FROM a workflow ("create automation out of it"). Four faces of one artifact, all through the same interface + runner contract: automation runnable, embedded Call node, agent tool (input schema = tool args, Finish = result), app/integration surface. Anti-garbage-pipe rules: (1) purity — everything enters via Start input + declared slots bound at instantiation, no ambient reach-ins; (2) one invocation seam — kickside.workflows:runner, no secondary run paths; (3) one grammar — interface derives from the graph only; (4) published-only callable; (5) spawned-child composition default, inline only for pure mapping transforms; (6) the definition+slots is one portable object, bindings/automations are separate portable artifacts. Consequences: trigger nodes leave the palette; builder simulate/run becomes "Run with input" (payload validated against Start); existing triggered definitions migrate by extracting the trigger into an automation binding (no flag day, legacy trigger_id bridged per W6.4); the Automations UI gains create-automation-from-workflow with the shared mapping editor. Greenfield authorization (owner, 2026-07-09): full refactors and REDUCTIONS toward this model are allowed — clean cut on the trigger grammar; legacy in-canvas-trigger definitions may be converted or dropped rather than dual-run; UX and compositional web components refactored accordingly. Tool-face note (owner FYI): the dataflow engine already runs flows declared inside tools/functions natively (wippy/dataflow flow.lua + compiler detect it) — workflow-as-tool must LOWER onto that native mechanism, not a parallel adapter; if an implementation lands as a custom adapter, reconcile it onto flow.lua in the same cycle.

## W11. Intent-first canvas (owner direction 2026-07-09, specifics pending sign-off)
Owner: "I basically just want to draw the arrows and blocks and let the system figure out the rest — even figure out when to insert, or maybe make invisible parallel/merge nodes, ask me 'hey, do you want to insert a function here? looks like we need something else.'" Design consequences (proposed):
1. EDGES ARE INTENT, NOT WIRING. Drawing A -> B always succeeds as a gesture. If schemas are compatible, it connects silently (compat validation already computes this). If shapes mismatch, the system does NOT reject — it offers, in order: (a) AI-drafted expr-lang transform on the edge (the existing one grammar, rendered as an edge glyph, inspectable on click, invisible otherwise); (b) "insert a node here?" (function/agent) when a pure mapping can't bridge semantically. The mismatch signal that today produces validation errors becomes the trigger for suggestions.
2. INVISIBLE PLUMBING IS RENDERING, NOT SEMANTICS. Fan-out (two+ edges out) and merge (two+ edges in) need no visible split/merge blocks — the canvas renders a small glyph on the join with configurable join semantics (wait-all default). The COMPILED document still contains the real, explicit graph: interface still derives from the graph, purity and inspectability keep W9 intact. Invisible means "not a block the user must place," never "not in the document."
3. PROACTIVE GRAPH ASSIST generalizes W10.2 from schema surfaces to graph surfaces: the same assist pipeline, fed graph context (the two node interfaces + the gap), drafts the bridging transform or proposes the inserted node. One assist backend family, no per-surface reimplementations.
W11.1 INTERACTION SPEC (owner direction 2026-07-10, verbatim intent: draw the line, it animates, a small prompt pops up "what do you mean by this?", type it, mapping happens — or when obvious, map automatically instead of asking):
- ON CONNECT: run the auto-map heuristic first. AUTO-APPLY ONLY when unambiguous — every required target field has exactly one name+type-compatible source candidate (exact/canonical name match); ambiguity of any required field means NO auto-apply. AMENDED (owner 2026-07-10): auto-map is SHOWN VISUALLY at the moment it happens — a transient anchored moment at the edge displaying the mapped pairs as compact source->target pills, fading after ~2-3s (click to pin/open mapper; reduced-motion safe) — plus the persistent hover/click WHY affordance as the trace. Never invisible, never a guess.
- AMBIGUOUS: the new edge enters a PENDING visual state (calm animation — flowing dash/shimmer, reduced-motion safe) and a micro-popover anchors at the edge midpoint: one-line intent input ("What should flow here?"), placeholder teaches by example. Typed intent -> the existing edge/binding assist drafts the mapping -> inline preview (compact mapper rows) -> accept applies, or open the full FieldMapper. Dismiss = edge stays connected, unmapped-required loudness applies (W15 bar).
- Everything lowers onto the one grammar (expr transforms) and the one assist family; the popover is sugar over the same seams. Auto-map decisions must be explainable: the affordance shows WHY it mapped (name+type match), per W13 honesty.
Guardrail (anti-garbage-pipe): everything the system inserts lowers onto existing vocabulary — expr-lang edge transforms and ordinary nodes in the compiled doc. No hidden second runtime, no magic that can't be opened and read. Empirical input: the sandwich-workflow UX audit (wf_ux_sandwich_audit.md) enumerates exactly where users are forced to do plumbing by hand; its friction list orders the rollout.

## W12. Workflows are the platform's behavior layer (owner direction 2026-07-09)
Owner: fewer primitives for users; keep parallel/loop etc. but every UI concept must be explainable at a glance, comparable to state-of-the-art authoring (n8n/Zapier class); complex workflows with every parameter tunable underneath, simple on the surface. Workflows fill gaps in business processes EVERYWHERE ("I go to CRM and say: what happens when the status of this contact changes? when the phone number changes?"), are reusable, shared as templates, loadable, packable together, and distributed via hub. Think holistically: dataflows are used everywhere — this is the universal behavior layer of the platform, not a feature page. Three components:
1. PRIMITIVE BUDGET (authoring vocabulary cap). The palette exposes a handful of user-facing concepts — step (any module's node), agent, condition, parallel, loop, human approval, Call workflow — each explainable in one sentence. Engine-level power (join semantics, retry, timeouts, expr transforms, run opts) lives behind progressive disclosure on those same primitives, never as additional palette entries. New engine capability != new user primitive; adding a palette concept requires an owner ruling.
2. ATTACH-IN-PLACE AUTHORING. Authoring starts FROM the business object, not from a workflows page: every module surface that emits events offers an "automate this" affordance (contact field, KB doc, inbox card, webhook, upload...) which deep-links into automation creation with the trigger point PRE-BOUND and the event's payload schema pre-fed to the mapping/Start assist. This is the W5 acceptance scenario turned into a UI contribution pattern: modules declare their event surfaces; the affordance is generated, not hand-built per module.
3. DISTRIBUTION: TEMPLATE -> PACK -> HUB. W7's module-shipped flow templates generalize into workflow PACKS: a portable group of templates (+ suggested bindings/automations) shippable as registry content, browsable and installable via hub exactly like modules, instantiable per workspace with slots bound at install (A10-6 portable object). Workspace grouping of installed/instantiated workflows follows the existing component/workspace model — no new container concept.
Guardrails: W8 discipline applies (each step must reduce concepts or serve a named consumer); W9 purity is what MAKES ubiquity safe (a workflow dropped anywhere cannot reach around its Start input); W11's intent-first canvas is the authoring face of the same budget.

## W13. Run/debug experience is a product pillar (owner directive 2026-07-09)
Owner: "clear super cool UI, no trash, good errors, and good debug." The run inspector and error surfacing are first-class product surface, not an afterthought:
1. GOOD ERRORS. No swallowed reasons anywhere in the execution path — every node failure carries a stable error code + human-actionable message from its true source (exit-schema validation says WHAT field failed; provider errors become typed, non-raw messages per the assist_unavailable convention). A terminal "Failed" with no reason is a defect by definition (live evidence: run 88444c66 agent node). Errors state what went wrong and how to fix it, in the interface's voice.
2. GOOD DEBUG. The run inspector exposes per-node input/output inspection (the data already exists in the run record — agent.action outputs, node.result payloads), the failing node's reason inline on the canvas overlay, and a re-run-with-same-input affordance. Debugging a run must not require API spelunking.
3. NO TRASH. The same design bar as the canvas: tokens-only --p-* styling, calm and consistent, zero leftover/duplicate chrome (redundancy audit discipline applies continuously). Every error/empty state is a directed moment (what happened -> what to do), never a raw dump or a dead end.
Sequencing: backend reason-propagation first (in flight), then the FE debug pass renders the enriched shapes; the UX-audit run view findings are the baseline.

## W14. Version discipline (owner direction 2026-07-09 — "state-of-the-art workflow solution")
Versioning is a product surface, not a storage detail. The typed-function model (W9) makes a SOTA version story cheap — the interface IS the graph-derived contract, so compatibility is checkable. Target model (specifics pending recon + owner sign-off):
1. LIFECYCLE: draft -> publish is the only transition; published versions are immutable; published-only callable (W9.4) already enforces the seam. Every publish records who/when.
2. RUN PINNING: every run executes and records ONE immutable published version; in-flight runs never migrate. The run inspector shows which version ran (W13 debug).
3. CONSUMER REFERENCES: every consumer face (automation, Call node, agent tool, embed) resolves through a declared pin policy — latest-published by default, explicit version pin available. No consumer ever silently executes a draft.
4. COMPAT AT PUBLISH: publishing a version whose Start/Finish/Error interface changed incompatibly against the previous published version triggers a consumer check — enumerate dependents (automations, Call sites, tools) and warn/require confirmation ("2 call sites depend on the removed field"). This is the differentiator the typed model earns; n8n cannot do this.
5. HISTORY UX: version list with who/when/interface summary; view an old version read-only; diff two versions (graph + interface); restore-as-new-draft (never mutate history).
6. TEMPLATES/PACKS (W12.3) carry their own version and record which template version an instance came from.
Discipline: W8 applies — build on the existing def CQRS/versions API, no parallel version store; recon first to map what already exists vs gaps.

## W17. Agent workflow traits (owner direction 2026-07-10)

## W8. Change discipline (owner directive, governs W1-W7, W9, W10, A10, and the vocab audit)
No massive change for change's sake. Every rectification must clear two bars: (1) it makes the system EASIER TO REASON ABOUT (fewer concepts, clearer seams, less implicit knowledge), and (2) it is needed by a real consumer (GTM, the canon, or a named second consumer). Working surfaces that already compose cleanly (sources, sinks, AWAIT arm, node sweep, dispatch seam) are KEPT and absorbed, not rewritten. When a proposed migration's cost exceeds its reasoning payoff, the old form stays as a documented lowering. The vocab audit's rectification list is filtered through this rule before anything lands in the ADR.

## W7. Continuity of module contributions (owner directive)
Modules continue to ship all three contribution kinds under v2 — the triad absorbs their wiring, it does not remove the surfaces:
- SOURCES — remain the way a module emits streams; they become/back trigger points (near-1:1 per recon).
- SINKS — remain the way a module accepts writes; they are runnables behind the one dispatch seam.
- FLOW TEMPLATES — module-shipped prebuilt workflow definitions (the inbox bridge/composite style): a module may ship complete, portable, instantiable definitions (+ suggested bindings) as registry declarations, instantiated per workspace with slots bound at install. This is the same artifact as gtm_pack workflow templates and rides the portable declaration object (A10-6). ## W5. Acceptance scenario (owner litmus test — the design passes only if this is natural and native)
"Use identity resolution as a building block inside a workflow that handles an event from a different component": e.g. webhooks (or inbox, or any module) emits its event -> a binding maps it into a workflow -> the workflow's first node is CRM's `Resolve contact` (the module's declared business node, config via its own WC, read-your-write output) -> downstream nodes consume the typed resolved-contact output. Requirements this encodes: (1) any module's capability is a palette node anywhere, discovered by sweep, zero glue code; (2) any module's event is a trigger point for any workflow; (3) typed outputs flow across module boundaries through the mapping primitive; (4) it feels native — same picker, same config panel, same run inspector regardless of which module contributed the piece. Every design review checks this scenario end to end.
